# meerkat-beams

MeerKAT primary-beam model handling: convert MdV mean beams to a beam dataset (BDS), serve interpolated and rotation-averaged beams from it through `BeamWizard`, and render it to `xradio`-compatible zarr stores or eidos-compatible FITS cubes. See https://doi.org/10.48479/wdb0-h061 for the upstream MdV beam data.

## LLM wiki

Deep reference for this repo lives in `docs/wiki/` — start at
[`docs/wiki/index.md`](docs/wiki/index.md), which routes to the rest. Each
page's frontmatter carries a `last_verified_commit`; a non-empty
`git diff <that commit>..HEAD -- <files the page covers>` means re-verify
the page before trusting it.

Maintenance rules:

- Read the relevant wiki page before working in a subsystem it covers.
- If a change invalidates or extends a page, update that page plus its
  `timestamp` and `last_verified_commit` **in the same session**, and add a
  line to `docs/wiki/log.md`. This applies to every page the change touches,
  `index.md` included — extending its Pages table is extending a page.
- `last_verified_commit` is **the last commit that changed the code the page
  covers** — not the pre-commit `HEAD`, and not the commit carrying the page
  edit. A stamp cannot name the commit that contains it: writing the hash
  changes the file, which changes the hash. Stamping with the `HEAD` you see
  before committing names a commit that predates the page's own edits, so
  `git diff <stamp>..HEAD -- <files the page covers>` is non-empty for a page
  you just verified and the staleness check fires on every fresh page. Commit
  the code first, then stamp the page at that commit in a docs-only commit —
  which leaves the covered files untouched, so the check stays clean.
  `log.md` is the exception and carries no `last_verified_commit`: it is a
  chronological record that covers no code, so only its `timestamp` moves.
- Specs and plans under `docs/superpowers/` are ephemeral working scratch —
  gitignored, never cited. Fold any durable fact they contain into the wiki
  before finishing a branch.

## Architecture — three layers + cabs

```
src/meerkat_beams/
├── utils.py                # shared: BeamWizard, Jones/Mueller algebra, group assembly, logging, zarr helpers
├── cache.py                # on-demand download + BDS cache (keyed on product name)
├── katbeam_bds.py          # synthesize a BDS-shaped dataset from katbeam (analytic)
├── _container_image.py     # container image tag (do not edit; see Conventions)
├── cabs/<cmd>.yml          # Stimela cab definitions (one per command)
├── cli/<cmd>.py            # hip-cargo-generated Typer + container dispatch
└── core/<cmd>.py           # plain-Python implementations (one per command)
```

One-to-one mapping: `cabs/foo.yml` ↔ `cli/foo.py` ↔ `core/foo.py`. Commands wired through `cli/__init__.py` into the `mbeams` Typer app.

**Rule:** code used by more than one core module lives in `utils.py`. `core/__init__.py` stays minimal. Core functions are plain Python and import from `utils.py`. See `docs/wiki/design-decisions.md` D7 for the rationale behind this layout.

### CLI ↔ cab generation (hip-cargo)

`cli/*.py` is **fully generated by `hip-cargo`** — not hand-written. The wrappers carry `@stimela_cab`/`@stimela_output` decorators, `parse_upath` parsers, `StimelaMeta` annotations, and auto-injected `backend` / `always_pull_images` Typer parameters that drive a native-first-then-container dispatch (`preflight_remote_must_exist` → native core call → `run_in_container` fallback resolved via `get_container_image("meerkat-beams")`).

Two generators, inverse of each other:

- `cli → cab`: the `generate-cabs` pre-commit hook runs `hip-cargo generate-cabs --module src/meerkat_beams/cli/*.py --output-dir src/meerkat_beams/cabs` on every commit. If a CLI signature changes, the cab YAML is regenerated automatically; the commit fails and you re-stage.
- `cab → cli`: `scripts/genfuncs.sh` runs `hip-cargo generate-function` once per cab and writes back into `cli/*.py`. Run it manually after editing a cab YAML directly.

**Round-trip discipline:** `cli → cab → cli` must compose to the identity. `tests/test_roundtrip.py` enforces this hermetically (generates cabs into a tempdir, regenerates CLI Python from each cab, line-diffs against `src/meerkat_beams/cli/*.py`). If it fails, either someone hand-edited `cli/*.py` (don't — edit the cab and run `scripts/genfuncs.sh`), or `hip-cargo` is non-idempotent (upstream bug). Modelled on `pfb-imaging/tests/test_roundtrip.py`.

**Don't hand-edit `cli/*.py`.** All changes flow through the cab YAML + regen. The core function in `core/*.py` is plain Python and can be hand-edited freely.

### Commands

| command | core | purpose |
|---|---|---|
| `mbeams mdv-beams-to-bds` | `core/mdv_beams_to_bds.py` | convert MdV `.npz` (or per-antenna mean-beam zarr) to a BDS (zarr) holding `jones`/`njones`/`stokes`/`nstokes` plus `mueller`/`nmueller` — see `docs/wiki/data-model.md` |
| `mbeams bds-to-xradio` | `core/bds_to_xradio.py` | render a BDS into a full `(time, frequency, polarization, l, m)` xradio zarr by interpolating the beam along parallactic-angle-rotated tracks, using a WCS image for pointing/time |
| `mbeams bds-to-fits` | `core/bds_to_fits.py` | render a BDS to **eidos-compatible** FITS beam cubes: `<prefix>_re.fits`/`_im.fits` hypercube (or `<prefix>_{ij}_{re,im}.fits` with `--output-eight`), on the BDS grid or a `--pixels`/`--diameter` resample; no image and no time axis — header contract in `docs/wiki/data-model.md` |

## Key abstractions in `utils.py`

`BeamWizard` attaches to a beam dataset and, optionally, an image (FITS or
xradio zarr), and provides beam interpolation, time-variable beam gain,
rotation-averaged beam maps, per-partition Mueller blocks (`partition_mueller`)
and full time/frequency zarr rendering. Downstream packages (`pfb-imaging`,
`QuartiCal`) call its public methods, so a method with no in-repo caller is not
dead code. Read these before touching it:

- [`docs/wiki/beamwizard.md`](docs/wiki/beamwizard.md) — the method-by-method
  contract: the `beam_model`, `group`, `average` and `freq_extrapolation`
  selectors and which combinations are refused, prefilter caching, off-cube
  policy, the optional-image construction paths, canonical `dim_names`.
- [`docs/wiki/data-model.md`](docs/wiki/data-model.md) — the BDS, xradio and
  FITS schemas it reads and writes.
- [`docs/wiki/design-decisions.md`](docs/wiki/design-decisions.md) — why:
  the band cache keyed on product name (D6), katbeam (D11), baseline groups
  (D12–D15), `partition_mueller` (D16, D17), frequency extrapolation (D19).

The MdV-2026 products carry `PLACEHOLDER` gdrive IDs until published:
`cache.ensure_product_bds` refuses to download one and tells you to stage the
input zarr by hand, which `scripts/stage_group_cache.py` does.

### Logging
`LOGGER` / `log` (same object). Console handler is kept on the module-level `CONSOLE`; change level via `set_console_logging_level(level)`. Don't create additional handlers.

### Zarr

zarr is **unpinned** so downstream applications choose zarr-python 2 or 3; everything we write is zarr **format 2** (`ZARR_FORMAT`) either way. Rules for new code:

- xarray writers pass `zarr_format=ZARR_FORMAT`; raw writes go through `zarr_open_group` / `zarr_create_array`, never `create_dataset`/`create_array` directly (the two majors disagree).
- Call `require_zarr_xarray_compat()` before every xarray zarr call and before any cache download feeding one. It raises `IncompatibleZarrStackError` for zarr-python 2 with `xarray>=2026.9`; raw zarr calls stay unguarded.
- Pass compressors to `to_zarr` encodings through `zarr_compressor_encoding()`.
- `ZARR_COMPRESSOR` (Blosc zstd, no filter) is applied only when a core function is called with `compress=True`. Any new filter must be lossless.
- In tests, assert codecs via the store's `.zarray` JSON, not `Array.compressor`.

Rationale, the `xarray>=2025.8` floor and the zarr 2 expiry date: `docs/wiki/design-decisions.md` D18.

## Conventions

- Python support policy: **3.11–3.13 full** (scientific stack, tested in CI); **3.10 lightweight only** — base install (CLI + hip-cargo container dispatch), no `[full]` stack, deliberately excluded from the CI test matrix (a dedicated `lightweight` CI job pins base-install + `mbeams --help` on 3.10 instead — do not add 3.10 to the test matrix). Test-group deps carry `python_version >= '3.11'` markers for the same reason.
- Runtime dep is `hip-cargo>=0.4.0`, resolved from PyPI — the transitional git-main pin is retired (see `docs/wiki/design-decisions.md` D8). The floor moves with upstream; what D8 settles is that the source is PyPI, not git. The scientific stack is under the `[full]` extra; `pyproject.toml` is the authoritative list. `dask-ms` is **not** a dependency (dropped for issue #28 — the package never imported it); the developer scripts that read Measurement Sets (`scripts/beam_orientation/ms_io.py`) use `arcae`, which arrives via `xarray-ms` in the `test` group. `katbeam` is in the `[full]` extra (resolved from PyPI) **and** pinned to git main in the `dev` and `test` groups — `BeamWizard(beam_model="katbeam")` uses it at runtime (issue #22), while the git pin stays because PyPI's only release (0.1) has no S-band model and has a narrower L table (900–1650 vs 856–1712 MHz). So **S-band katbeam works only in a dev checkout**, not from a published `[full]` install. The git pin knowingly reintroduces the pattern D8 retired for hip-cargo, scoped to dev/test only — see `docs/wiki/design-decisions.md` D11.
- Ruff: `line-length=120`, `target-version=py311`, rules `E,F,I,N,W` with `E741`/`N806` ignored (domain names: `l`, `m`, `I`, `S`, `Sinv`). Pre-commit runs `ruff-check --fix` and `ruff-format`.
- Core function signatures mirror their CLI signatures (same names/defaults) with plain types. Don't move Typer conversions into core. CLI passes `parse_upath`-parsed path objects directly (no `str(...)` coercion); core accepts anything `str`-coercible / path-like.
- Commits: conventional prefixes, **enforced** by `conventional-pre-commit` at the `commit-msg` stage. Allowed types: `feat fix refactor perf docs deps chore ci style test build`. Fresh clones need `pre-commit install --hook-type commit-msg` — plain `pre-commit install` does not wire up the `commit-msg` hook.
- Version bumping via `tbump` (config in `tbump.toml`), **PEP 440**: `X.Y.Z`, optional `aN`/`bN`/`rcN`, optional `.postN`.
- `CHANGELOG.md` is **generated, not hand-edited**: a `tbump` `before_commit` hook runs `uvx git-cliff --tag v<new> -o CHANGELOG.md` and stages it, so the changelog lands inside the release commit. `-o` rewrites the whole file from git history every time, so hand edits do not survive a release — fix changelog problems in `cliff.toml` (grouping rules, `commit_preprocessors`), never in `CHANGELOG.md`.
- **Container image tag: leave it alone.** `src/meerkat_beams/_container_image.py` and the `image:` line of every cab stay at `:latest` on every branch — do not point them at a branch name or a version. `tbump` pins the tag in the release commit and `update-cabs.yml` resets it to `:latest` on `main`. `publish-container.yml` publishes on a merge to `main` (`latest`), on a version tag, and on a manual run — never for an open PR. Publishing a feature-branch image for users to test (`gh workflow run publish-container.yml --ref <branch>`, image tag = branch name with `/` → `-`) and retagging the branch to match are the maintainer's manual steps, not an agent's; see `docs/wiki/design-decisions.md` D10.

## Running things

```bash
# Dependency groups do NOT imply the [full] extra. Omitting `--extra full`
# actively UNINSTALLS the scientific stack (zarr, matplotlib, numcodecs,
# gdown, s3fs, ...), because
# `uv sync` makes the environment match exactly what you asked for. Some of
# it survives transitively via the test group, which makes the breakage
# confusing rather than obvious. Always pass `--extra full` for real work.
uv sync --group dev --group test --extra full   # install dev + test deps
uv run ruff format --check .          # format check (CI)
uv run ruff check .                   # lint (CI)
uv run pytest -v                      # full test run
uv run pytest -m unit                 # unit tests only
MBEAMS_OFFLINE=1 uv run pytest -m unit  # strict-hermetic: no cache warm-up
uv run mbeams --help                  # CLI

# Regenerate CLI Python from cab YAMLs (manual; pre-commit handles cli → cab).
bash scripts/genfuncs.sh
```

CI (`.github/workflows/ci.yml`) runs ruff + `MBEAMS_OFFLINE=1` pytest on Python 3.11–3.13, plus a `latest` job (newest xarray + zarr past the lock), a `zarr2` job (zarr-python 2), a `floors` job (xarray pinned at its declared floor — keep the pin in step with `pyproject.toml`), and a `lightweight` job that pins the 3.10 base-install guarantee (no test suite there — see the Python support policy above). The two jobs sync differently: lint uses `uv sync --group dev`, the test job uses `uv sync --group test --extra full` — **no `dev` group**. So anything a test needs must be in the `test` group, not just `dev`, or the test will skip silently in CI (this is why `katbeam` is listed in both). Commit message containing `[skip checks]` skips the CI job. Docker image built from `Dockerfile` (python:3.11-slim, installs `.[full]`; no `git` — the layer for the retired hip-cargo git-main pin is gone, see `docs/wiki/design-decisions.md` D8).

## Tests

Located in `tests/`. Markers: `unit`, `integration`, `slow`. Synthetic inputs (BDS, mean-beam zarr, npz, FITS and zarr images) come from `tests/_synthetic.py` — use those builders rather than inlining a new one.

- `uv run pytest -m unit` is the hermetic subset; everything in it builds its inputs in `tmp_path`.
- `test_roundtrip.py` pins `cli → cab → cli` idempotency. **If it fails, do not hand-fix `cli/*.py`** — edit the cab and run `scripts/genfuncs.sh`.
- `test_cli_native.py` runs every command through the real CLI with `--backend native`. The CLI hands core functions `UPath` objects, so this is what catches a core function calling `str` methods on a path (#38). A new command needs a test here.
- `integration` tests need real beam products named by environment variables (`MBEAMS_BDS_PATH`, `MBEAMS_IMAGE_PATH`, `MBEAMS_REFERENCE_BDS_<BAND>`, `MBEAMS_MK2026_BDS_PATH`, `MBEAMS_MKE_BDS_PATH`) and **skip silently** without them. The README's Development section has the table of which test needs what, the cost, and how to build the 2026 BDSs. If you expect a test to run, check the skip reason first (`pytest -rs`).
- The conversion regressions use ~27 GB peak RAM and ~5.4 GB of `tempfile` scratch per band; point `TMPDIR` at a disk with room.

Set `MBEAMS_OFFLINE=1` to skip the L-band cache warm-up in `conftest.pytest_sessionstart`; it also sets astropy's `iers.conf.auto_download = False`, because a failed IERS download is retried by every parallactic-angle test (30–75 s each). CI sets it. Online runs keep live IERS tables.
